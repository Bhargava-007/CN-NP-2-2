# JOURNEY

## Week 0: setup
**Decision:** Run the lab in a dedicated WSL2 distro "setu-lab" (a local clone of my existing Ubuntu 26.04), with Docker (docker.io) and containerlab inside it, driven by the kit's SetuLab module from Windows PowerShell 5.1. Everything installed lives inside that one distro, so cleanup is a single wsl --unregister.
**Alternative rejected:** Running the kit's Install-SetuPrerequisites (Visual Studio Build Tools, Wireshark, a fresh Ubuntu 24.04; several GB on Windows, hard to remove cleanly), and installing the lab into my existing Ubuntu in place (cleanup not provable).
**Cost accepted:** The kit was written for PowerShell 7 and Ubuntu 24.04; I run 5.1 and 26.04, so a cmdlet may misbehave and I check each one as I use it. The containerlab apt repo is unsigned (trusted=yes), confined to setu-lab. The clone costs about 3 GB of disk.
**Evidence:** INSTALL-LEDGER.md, section "Week 0 verification" (Test-SetuHost all OK except optional mac802154_hwsim).

## Week 1
**Decision:** Replaced the shipped `byte_stream.c` and `webget.c` with my own implementations in `stack\src\` (originals stay in git history, commit `e09d168`), and patched `Invoke-SetuWsl` so the PS7-targeted kit runs on Windows PowerShell 5.1. Captured packets at three taps and tested my ByteStream (1 MB through capacity 2, clean under ASan/UBSan) and `webget` against the kernel.
**Alternative rejected:** Keeping the shipped reference code and only reading it (rejected: I must defend my own code). Installing PowerShell 7 to avoid patching the kit (rejected: extra install, footprint, the patch was 8 lines).
**Cost accepted:** Kit targets PS7/Ubuntu 24.04 and I run 5.1/26.04, so I carry a local patch for PS 5.1. Stock `Invoke-SetuCapture` cannot write to `/mnt/c` as user `tcpdump`, so captures go to `/tmp` and are copied manually. The distro idles out and loses veth links, requiring a hidden `sleep infinity` keepalive and redeploy after shutdown instead of patching the cmdlet now.
**Measured:** RTT `dev01` to `srv01`, 3 runs of 1000 probes, median p50 `0.078 ms`, p99 `0.201 ms` (range `0.167-0.204`), `0%` loss; delay is processing, not transmission or propagation, which is the opposite of a real campus link.
**Lesson:** Wire efficiency of an 11 B payload is `14.3%` on the wire (COMPUTED).

## Week 2
**Decision:** Measured one impairment at a time (delay, loss, rate), always on both ends because `netem` is egress only, and confirmed baseline after each. Found that a packet-count queue limit does not bound delay and replaced it with a time-bounded `tbf` queue.
**Alternative rejected:** Trusting my own arithmetic for queue delay (rejected: three predictions failed; 50 packets held 14-19 KB each, MTU 9500, offload and GSO cap had no effect). Reporting means or single runs (rejected: percentiles, 3 runs, range).
**Cost accepted:** `BUDGET.md` v0 is NOT YET PROVEN: `200 Mbit/s` with an EF flow is unmeasured, only `100 Mbit/s`, 1 TCP flow, one direction shaped. Cause of large queued packets and of the `7 ms` plateau above the knee not identified. `Measure-SetuThroughput -Runs 1` fails under `StrictMode`, so some UDP/TCP throughput points are missing; the 1000-packet case has 1 run.
**Measured:** idle RTT `p50 0.09` / `p99 0.269 ms`; 1000-pkt queue loaded `p50 269 ms`; `tbf` loaded `p50 3.86` / `p99 5.0 ms` at `99.2 Mbit/s`; knee between `95M` and `100M` offered (`p50 0.06 -> 7.2 ms`).
**Lesson:** Bound queues in bytes or time, not packets.

## Week 3
**Decision:** Hierarchical address plan: one `/20` per site with VLSM inside, and `/64` per segment from a `/52` per site (4 site routes plus infra instead of about 19 with tight VLSM). The resource constraint is routes and operator comprehension, not addresses. Second decision: Kea is installed and started by hand after deploy while `kea01` idles on `sleep infinity`.
**Alternative rejected:** Tight VLSM packed from `10.20.0.0`, and boot-time `apt` install in the `kea01` container command.
**Cost accepted:** Low address efficiency (`COMPUTED` in `ADDRESS-PLAN.md`; `BLD-C` `22.9%` today, `36.7%` at 5 years) and most of the `/16` unused, with host counts as `ASSUMPTION`s. One extra manual step per deploy for Kea, not yet scripted.
**Measured:** Relayed DHCP lease works (`dev01` `10.20.32.20/23` from Kea `10.20.48.9` via `rtr`). Three faults reproduced with full hypothesis/test/evidence/fix/verify: missing relay (no `DISCOVER` in Kea log), wrong scope (`DISCOVER` arrives, `"No subnet matches relay address: 10.20.32.1"`), server down (`0` Kea processes, no lease); fault 3 has no wire capture (empty twice, cause unknown). `check_plan.py` passes `7/7` checks, proving self-consistency rather than that the host counts are right.
**Lesson:** Three of my own tests were invalid before they were valid (pool and reservation not moved with the subnet; `docker top` shows host PIDs while `kill` needs in-container PIDs; a stale Kea held port 67), so a lease or failure only counts as evidence after confirming which process answered. Also: Kea 2.2.0 syntax differs from newer docs.

## Week 4
**Decision:** Write own `http_server.c` and `dns_resolve.c` from scratch, replacing the shipped files (shipped originals stay in git history at `e09d168`), because I must defend every line. Second decision: reconcile the DNS zone to `ADDRESS-PLAN.md` and add the reverse zone.
**Alternative rejected:** Edit the shipped starter/reference, and keep the kit's illustrative addresses.
**Cost accepted:** More time, and the code has only been built and run on Linux (`gcc` in `setu-lab`), not on Windows. Kit zone files changed, serial bumped to `2026112501`.
**Measured:** HTTP server passes `GET`, `HEAD`, `404`, `405+Allow`, pipelining (`2` responses), chunked with extension and trailer, `CL` body, one-byte-per-send, bad chunk size `400`, `gzip` TE `501`, huge `CL` `400`, `HTTP/2.0` `505`, `20 KiB` header `431`, `100`-request cap (`100` of `105` answered), idle close at `6 s` (`5 s` timeout plus measurement overhead); Edge rendered it via `localhost` forwarding on port `8090`. Resolver output matches `dig` for `A`, `AAAA`, `CNAME`, `MX`, `NS`, `TXT`, `SOA`; `NXDOMAIN` exits `3`; `PTR` matches `dig -x` after the reverse zone was added. Not tested: `TC` to TCP fallback, wrong-source/wrong-ID rejection, Windows build, `Start-W03Kea.ps1`, `NXDOMAIN` via `dig`.
**Lesson:** Three of my tests were invalid before the code was wrong: `grep -c` on glued responses (body without newline), `nc -q` quitting early (`88` vs `100`), and a leftover lab holding port `8080` via `docker-proxy` (empty replies). Windows `nslookup` could not reach `5353` because Chrome owns UDP `5353`. Check what actually answered before blaming the code.
**Addendum (Measured):** HTTP server under ASan/UBSan: `GET`, `404`, `HEAD`, `405`, `431` all as before, `0` sanitizer errors (chunked body not covered: test sent chunked `POST`, got `405`). DNS resolver: wrong ID and wrong question echo ignored; `TC=1` falls back to TCP and prints answer (fake server, 1 run each). Not tested: wrong-source rejection, Windows builds, `Start-W03Kea.ps1`.

## Week 5
**Decision:** Wrote own `server_models.c` (`threads`, `select`, `poll`, `epoll`; bounded output queue with backpressure, idle sweep, `431` on oversize input), replacing the shipped one; wrote a C load client after the Python client proved CPU-bound.
**Alternative rejected:** Multi-process Python client; kept shipped starter handler (silent drop, unchecked `send`).
**Cost accepted:** Linux only so far (no `WSAPoll`/IOCP), per-connection 64 KB `outbuf` allocated eagerly, 4096-sample cap per stats window, `threads` mode has no send timeout and reports stats only on `accept`.
**Measured:** (3 runs, loopback, same host, `-O2`, 50 active connections, 3-byte responses, C client `K=1`, `p50`/`p99`): `epoll` rps `98k-106k` and `p99` `0.83-1.02 ms` flat from `N=100` to `10,000`; `poll` `112k` rps / `0.93 ms` at `N=100` falling to `8.5k` rps / `8.6 ms` at `N=10,000`; `select` matches `poll` to `N=500` and refuses `fd >= 1024` (`10,000` idle test: `1,018` open, `8,983` refused); `10,000` idle on `epoll` and `poll` held (ASan build RSS `246 MB`). Functional: single, pipelined x5, `431`, backpressure with slow reader (second client served, `backpressured=158`) pass in all four modes under ASan/UBSan. Caveats: client and server both near one core at `K=1` so absolute rps is a joint ceiling; constant `~48 ms` max in every run unexplained, not reported; Python client series superseded (client-limited, `python` at 100% of one core); `epoll` skip-`MOD` change gave no gain.
**Lesson:** Three failures were in my reading of results, not the code: client was the bottleneck, a bad `INFERRED` claim (`epoll_ctl` cost) was withdrawn after measuring, and a UTF-16 file from PowerShell `tee` broke a parser. Check what limits the measurement before drawing a curve.
**Not done:** Accept-queue behaviour, `select`/`poll` slow-reader on `threads` mode, Windows builds, reassembler start.

## Week 6
**Built:** `reassembler` (fixed window + per-byte flag), `receiver` (window = `min(bs_remaining, 65535)`, no window scaling), `ip_tcp` (IPv4+TCP codec, RFC 1071 checksum), `sender` (RTO via Jacobson/Karels, Karn both halves, fast retransmit on exactly 3 dup ACKs, no storm, zero-window probe of 1 byte), `tcp_connection`, and `setu_tcp` TUN wiring.
**Decision:** `Sender` owns SYN/FIN retransmission (one timer, one backoff).
**Alternative rejected:** Handshake handled separately in `tcp_connection`.
**Cost accepted:** `Sender` is more complex; no `TIME_WAIT` linger; fixed local port `40000`; full-segment ACKs only (partial ACK inside a segment ignored); one segment per `stdin` read so some short mid-stream segments (e.g. `892` and `1176` bytes seen in capture).
**Measured:** Interop Gate `12 of 12 GATE-PASS` (clean, delay, jitter, loss, reorder, smallmtu, each send and receive), `1,048,576` bytes, hashes equal, single run per combination. Unit tests: ASan/UBSan clean; `ctest 9 of 9`. In-memory `5%` loss 1 MB test passes.
**Limits:** `netem` is egress on `tun144`, so it impairs kernel-to-us only; loss send showed `retx=0`, meaning our retransmit path was NOT exercised by the gate, only by the in-memory loss tests. `parse_drops` of `0-2` per run are probably IPv6 multicast listener reports (inferred from one capture, not proven). Gate result is one run each.
**Lesson:** Two test expectations were wrong when written (`receiver` window test expected 2 bytes but stream held 4; `sender` Karn test assumed no sample after the SYN ack) and were corrected after reading the code; the `Receiver` and `Sender` were right both times. Also the shuffle test replays segments over several passes, so it does not test one-shot arrival.
